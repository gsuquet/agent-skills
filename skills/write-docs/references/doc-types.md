# Doc types

Read this at step 2 when the type table matches no row or two rows. Each type answers one reader
need. Find the reader's situation in the boundary table first; read a type section when the table
row still leaves a doubt.

## Boundaries

| The request looks like | It is | Because |
|---|---|---|
| "document how to deploy X" for someone new to X | tutorial | the reader learns; a working result matters more than their own goal |
| "document how to deploy X" for the team that runs X | how-to | the reader knows X and has a goal |
| "document how to deploy X" when X is down | runbook | the reader responds to a symptom, under time pressure |
| "document the config of X" | reference | the reader looks up a key; there is no task |
| "document the architecture of X" | concept | the reader wants to understand; there is no task |
| "document why we chose X" | RFC | a decision is recorded only through an accepted RFC and its ADR |
| "write a design doc for X" | RFC | a design that others must agree on is a proposal |
| "update the README" with a long procedure | how-to | the README keeps the quick start and links the how-to |

When the request needs two types (for example a tutorial and the reference of the flags it uses),
write two docs that link to each other.

## README

The landing page of a repository or folder. It answers "what is this, and how do I start?" in
under a minute. It holds the quick start, the most common tasks and links. It never holds a long
procedure, an architecture explanation or a full option list: those go to a how-to, a concept and a
reference it links.

## Tutorial

A lesson. The reader is new and learns by doing one guided path that always works. The author
chooses everything: tools, names, options. It never offers alternatives, never explains at length
and never depends on the reader's own environment beyond the listed prerequisites.

## How-to

A recipe for one goal the reader already has and understands. It assumes the basics, lists
prerequisites, gives numbered steps and a check that the goal is reached. It covers the real
variations the reader meets (as separate how-tos when they diverge), not the theory.

## Reference

Facts to look up, complete and in the same shape for every entry: commands, flags, config keys, API
fields, limits, defaults. Its structure mirrors the thing it describes. It is generated when a
generator exists. It never holds steps or opinions.

## Concept

An explanation: how something works and why it is built this way, with the trade-offs and the
history that matter. The reader reads it away from the keyboard. It links ADRs for the decisions
and how-tos for the tasks, and holds neither.

## Runbook

The response to one alert or symptom in a running system, written for an on-call engineer who did
not build the system. It goes from what they see to a recovered service: symptoms, impact,
read-only diagnosis, mitigations, rollback, escalation, verification. One runbook per alert. It
differs from a how-to in its trigger (an alert, not a goal) and in its reader (under pressure).

## RFC and ADR

An RFC is a proposal for a change that is hard to undo or that can break more than what it changes;
the deciders accept or reject it. An ADR is the frozen Decision section of an accepted RFC,
generated by `scripts/rfc-to-adr.sh`. The RFC section of SKILL.md holds the rules.
